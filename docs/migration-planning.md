# Mapping & Migration Planning — 1.4.2

Open `/admin/#/migration`, create a project, and complete Discovery. Create the destination content types in the existing Content Types section first. The mapping editor lists their actual fields and required flags. Choose a destination for each source type (empty excludes it), map title/slug and `data:<handle>` fields, and select copy/text/number/boolean/date/datetime/json conversions. `meta:<key>` addresses DLE xfields or WordPress metadata; core fields are title/body/excerpt/slug/date/categories/tags. Copy of HTML does not execute it in planning; import must sanitize content before publication. No PHP serialization, shortcodes or plugin code is executed. Non-public source statuses cannot map directly to published; unknown statuses default to draft. Dates without timezone are interpreted as UTC for datetime conversion; verify source timezone before execution.

Conflict policy `fail`, `skip`, `update` or `create` applies to existing same-type, same-locale slugs. `create` chooses a free numeric suffix; duplicate source claims on the same target are blocked. `update` plans a replacement payload, including nullable unmapped fields, not a merge. Only existing target types are supported. Category/tag source values may be mapped to fields; taxonomy entity creation, relationship/media remapping, menu/SEO routing and cross-type URL collision validation belong to later stages.

Run Dry Run to inventory real content and author identifiers. For each source user, enter an explicit UUID of an active target user, `create` (a future viewer account requiring activation and a unique valid email), or `skip`. Email matches are surfaced as conflicts, never linked automatically. Unknown or unmapped users block approval; source user emails and raw content are not included in the plan. No user account is created, updated or activated by planning. User IDs for WXR/DLE can be source logins; WordPress DB/REST use numeric IDs. User mapping is a JSON object; use the IDs shown in the Dry Run table. The Users screen provides target UUIDs.

Save mapping, run Dry Run, resolve all conflicts, repeat Dry Run and approve. Approval rereads the source and destination and verifies the exact plan SHA-256, then stores the approved timestamp using project revision CAS. A mapping change or rescan invalidates the plan. Source/target changes between Dry Run and approval reject approval. Approval is a read-only point-in-time check, not a lock on the remote site or a migration execution token: future execution MUST revalidate the hash and acquire its own operation/target locks before writing. Plans include per-record action, target ID/slug, author ID and normalized payload SHA-256, plus source/target/mapping fingerprints. Raw payloads are reread for future execution, not stored in public project JSON. Projects and plans use the existing protected atomic file store and backup lease. The JSON export contains source identifiers and target metadata; treat it as sensitive.

## Limits and supported sources

- WordPress DB / DLE: existing operator allowlist, SELECT-only credentials, TLS policy and read-only transaction. UTF-8 connection for conversion from stored charsets. WordPress post meta uses the first repeated key; DLE xfields supports pipe-delimited values. DLE static pages default to draft. WordPress attachments/revisions/menus/internal types are excluded from this content plan.
- WordPress REST: only visible standard posts, pages and users, paginated with fixed endpoints. Private/custom content and email may not be exposed. Unavailable users are reported, authors from visible records still require explicit mapping. REST access follows existing HTTPS allowlist; no arbitrary destination or redirects.
- WXR: same 8 MiB cap and XMLReader validation as discovery; no DTD or external entities. WXR author records are not the entire user database.
- Limits: 500 content records, 500 user records, 16 MiB inventory, 10,000 WordPress metadata rows and 10,000 target entries per selected type. Exceeding limits aborts rather than silently approving a truncated inventory. Larger sources need split exports or the later streaming migration stage. SQL/REST reads are bounded; REST has a 25-second request budget checked between calls.
- Scope: this is planning only. No target writes, new SQL migrations, full taxonomy/media import, actual identity migration, or execution/rollback yet.

## API and permissions

`GET /api/v1/migration/catalog` (`migration:read`), `PUT /api/v1/migration/projects/{id}/mapping` (`migration:write`), `POST .../plan` (`migration:run`, `users:read`), `POST .../approve` (`migration:run`, `migration:write`, `users:read`). All mutations use revision and CSRF/session policy. The mapping body contains `revision` and `mapping`: `types` (source type -> `{target,fields}`), `statuses`, `users`, `locale`, `conflict`. Each field rule is `{from,transform}`. Approval takes `revision` and `sha256`. All reports are no-store. Existing 1.4.1 projects continue to work without modification.

## 1.4.8 execution limits and checkpointing

Version 1.4.8 increases the bounded inventory ceiling to 5,000 content items and 5,000 users (64 MiB normalized JSON, up to 32 MiB WXR input). These are hard validation caps, not streaming/unlimited imports. Use the new `migration:execute`/`migration:resume` operator CLI and read [Migration Execution & Recovery](migration-execution-recovery.md) before running. Legacy atomic CLI execution remains available for compatibility, but it does not produce resumable checkpoints.
