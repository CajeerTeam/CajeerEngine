# CajeerEngine 1.9.2 — Migration Center Production

## Назначение и совместимость

Этот релиз исправляет **рабочие пути записи** DLE/WordPress: обычный SQL-импорт, пакетный импорт и incremental sync проверяют конкретную ревизию целевого материала перед обновлением. Полученная после утверждения плана правка редактора не должна быть перезаписана. Это относится к режиму конфликтов `update` и требует хранения ожидаемой ревизии в одобренном плане.

Сохранены ограничения источника: до 5000 материалов и 5000 пользователей на проект, до 64 МиБ данных планирования, до 32 МиБ WXR, ограниченный локальный медиакаталог. Для WordPress через БД полная выборка `postmeta` ограничена 100 000 строками, а связи рубрик/тегов — 10 000. При превышении этих порогов планирование теперь **завершается ошибкой**, а не неполной инвентаризации. Разделите источник на непересекающиеся партии, учитывая все метаданные, либо подготовьте проверяемую отдельную миграцию.

Обновление **не содержит изменений SQL-схемы**. Изменён формат утверждённых планов с действием `update`: добавлено `expected_revision`, включённое в SHA-256 плана. Нельзя обновлять исполняемый код посреди начатой миграции 1.9.1: старый checkpoint может не содержать защищённой ревизии, и продолжение теперь намеренно отклоняется. Сначала завершите старую транзакцию в старом коде или восстановите полную копию до её начала; только затем устанавливайте 1.9.2 и утверждайте новый план.

## Подготовка

1. Разверните копию production-сайта на staging с тем же движком БД и хранилищем медиа. Для исходного DLE/WordPress предоставьте **только читающие** учётные данные; зафиксируйте состояние источника на время инвентаризации.
2. Проверьте `CONTENT_STORAGE=database`, `CMS_STORAGE=database`, настройки secret vault и наличие всех миграций. Остановите сторонних writers и scheduler. Проверьте доступность BackupManager и возможность полного восстановления.
3. Создайте проект, выполните Discovery → Mapping → Dry Run → Approve в интерфейсе Migration Center. Проверьте количество материалов, пользователей, пропуски, ограничения метаданных, URL и список конфликтов.
4. При `update` сверяйте ожидаемые ревизии каждого целевого материала. Не допускайте редактирование CMS между утверждением и переносом. При несовпадении ревизии загрузите новый dry run и получите новое подтверждение — не изменяйте журнал или курсор вручную.

## Выполнение и возобновление

```bash
php bin/cajeer backup:create
php bin/cajeer migration:execute PROJECT_ID PLAN_SHA256 --yes --batch=50 --max-batches=1
php bin/cajeer migration:status PROJECT_ID
php bin/cajeer migration:resume PROJECT_ID PLAN_SHA256 --yes --batch=50
```

`PROJECT_ID` и `PLAN_SHA256` берутся из утверждённого проекта; это не буквальные идентификаторы. Промежуточный прогон сохраняет курсор и журнал. Возобновление возможно только при неизменных source SHA, плане и проверяемом backup. При ошибке транзакция текущего batch откатывается, но уже завершённые партии остаются; maintenance остаётся включённым. Не заменяйте ошибку на `skip` без нового утверждения.

После завершения контента проверьте импорт медиа (строго из локального проверенного зеркала) и SEO. Экспорт URL-карты храните вне публичной директории; используйте только адреса старого подтверждённого домена. Медиа и SEO — отдельные этапы, не входящие в транзакцию контентного batch.

```bash
php bin/cajeer migration:media-import PROJECT_ID /secure/source/uploads --yes --origin=https://old.example.com
php bin/cajeer migration:seo-import PROJECT_ID --yes --origin=https://old.example.com --legacy-map=/secure/urls.json
php bin/cajeer migration:validate PROJECT_ID
```

Не считайте перенос завершённым при ненулевом exit code этих команд. Сравните исходные и конечные количества контента, статусы публикации, авторов, идентичность файлов/хешей, неразрешённые ссылки, SEO-маршруты, директивы Rank Math/Yoast `noindex` и пересечения редиректов. Снимите контрольную копию после успешной проверки и отдельно согласуйте cutover.

## Аварии, сохранность и откат

При `RevisionConflict` целевая запись **не перезаписывается**, а текущий SQL-batch и курсор остаются прежними. Фиксируйте источник, сверяйте редакторские правки и только после решения оператора переутверждайте план или выполняйте полный откат. Для already-started checkpoint редактирование approved plan запрещено, поэтому используйте сохранённую контрольную копию перед новым проектом.

```bash
php bin/cajeer migration:status PROJECT_ID
php bin/cajeer migration:rollback PROJECT_ID VERIFIED_BACKUP_ID --yes
php bin/cajeer maintenance:status
```

Откат восстанавливает **полную БД и файлы** из проверенного backup и может удалить любые изменения, выполненные после его создания. Не выключайте maintenance до независимой проверки корректности данных и публичных маршрутов. Вывод в stdout/stderr и файлы контрольных сумм должны сохраняться в защищённой операторской папке без секретов и пользовательских данных.

## Acceptance на реальном окружении

- `php tools/migration-production-regression.php` — регрессии versioned CAS и невозможности незаметно усечь MySQL-метаданные/таксономии; запускается в PR и Release CI.
- `php tools/migration-execution-regression.php --require-db` — реальный SQLite batch, остановка после изменения ревизии материала, целостность журнала и курсора.
- `php tools/wordpress-migration-regression.php --require-db --require-xml --require-mysql` и `php tools/dle-migration-regression.php --require-db --require-mysql` — существующие интеграционные тесты, требуют подготовленных зависимостей и сервера MySQL/MariaDB.
- На staging отдельно исполните полный перенос типового проекта на поддерживаемой конфигурации, отказ посредине batch, повторный запуск, перенос медиа, проверку редиректов и откат. Запишите контрольные суммы source/dist, версии и результаты. Без этих проверок релиз **не является сертифицированным production GA**.
