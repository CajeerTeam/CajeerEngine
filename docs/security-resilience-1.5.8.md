# CajeerEngine 1.5.8 — Security & Resilience Hardening

## Реализованное поведение

- `SecretVault`: authenticated XChaCha20-Poly1305 encryption, AAD привязывает секрет к владельцу и назначению, `v2:<kid>:<base64>` фиксирует идентификатор активного ключа. Существующий формат v1 (base64 без префикса) читается с текущим или одним из явно указанных прежних ключей; новые записи всегда шифруются активным ключом. Неизвестный ключ, ошибка целостности и неправильный контекст приводят к отказу.
- `php bin/cajeer keys:status`: полное чтение и проверка подлинности секретов в реестре интеграций, проектах миграций (включая WXR), журнале серверной аналитики (шифротексты активных грантов откладываются до завершения гранта), SQL `analytics_connections` и `ce_oidc_transactions`; выводит только счётчики и идентификаторы ключей, не секреты. Не изменяет шифротексты.
- `php bin/cajeer keys:rekey --yes`: реальное повторное шифрование найденных записей активным ключом. SQL-таблицы обрабатываются транзакционно, файлы — атомарной заменой, интеграции — под блокировкой реестра; каждый этап идемпотентен. Глобальная эксклюзивная блокировка останавливает конкурирующие операции, а после сбоя команда может быть запущена повторно с тем же набором прежних ключей. Нет автоматического удаления старых ключей или незащищённой ротации через HTTP.
- `php bin/cajeer keys:generate --file=/secure/external/unique-key.txt`: создание нового 32-байтового ключа вне каталога CMS, файл 0600. Команда не печатает сам ключ.
- Integrations: durable circuit breaker на подключение. После пяти временных ошибок (сеть/HTTP 408, 425, 429 и 5xx) новые попытки блокируются на 60 секунд. Затем ровно один процесс выполняет пробный запрос, пока остальные получают `circuit_open`. Успех и постоянные 4xx закрывают breaker; повторная временная ошибка открывает заново. Результаты не содержат секретов или удалённых ответов. Очередь продолжает использовать собственные повторные попытки с backoff.
- OIDC: ограниченный повтор GET-запроса discovery/JWKS на временной ошибке; обмен одноразового authorization code и introspection POST не повторяются. Ответ ограничен в процессе чтения 256 KiB, TLS проверяется, редиректы и прокси запрещены. Ошибка IdP остаётся отказом во внешней авторизации (fail closed), локальные входы не меняются.
- Public HTTP transport: только GET/POST с ограниченным размером ответа; rate limit: private файлы 0600 и fail-closed на повреждённых счётчиках. `security:doctor` проверяет конфигурацию ключей, не раскрывая их.

## Процедура ротации в production

1. Убедитесь в наличии **проверенного восстанавливаемого backup** CMS и БД и сохраните ключи backup отдельно. Приостановите фоновых работников и соблюдайте окно обслуживания. Запускайте команды от системного пользователя приложения; `.env` должен быть защищён правами доступа.
2. Создайте ключ: `php bin/cajeer keys:generate --file=/etc/cajeer/rotation-2026-11.key` (каталог `/etc/cajeer` должен существовать и быть закрыт для посторонних).
3. Задайте в `.env` новый `INTEGRATIONS_KEY=base64:<НОВЫЙ_КЛЮЧ>` и прежний `INTEGRATIONS_PREVIOUS_KEYS=base64:<СТАРЫЙ_КЛЮЧ>`. Если ранее использовали `APP_KEY` вместо `INTEGRATIONS_KEY`, укажите прежний `APP_KEY` в списке decrypt-only. **Не меняйте `APP_KEY` в ходе ротации vault** — он применяется и для других задач (например, подписанные media URL).
4. При отдельном `SKIF4ER_ID_TRANSACTION_KEY` аналогично задайте `SKIF4ER_ID_TRANSACTION_PREVIOUS_KEYS` и новый активный ключ. Если ранее OIDC использовал общий ключ, перечислите прежний общий ключ при переходе на отдельный. Значения списка разделяются запятыми; до восьми предыдущих ключей.
5. Выполните `php bin/cajeer keys:status`; ошибки чтения / неизвестный ключ требуют исправить keyring и **не удалять старый ключ**. Затем `php bin/cajeer keys:rekey --yes`; повторите `keys:status`, ожидая `changed: 0`, `deferred: 0`. Команда использует глобальную эксклюзивную операционную блокировку; при действующих запросах завершится отказом вместо прерывания операций.
6. Перезапустите PHP-процессы и фоновых работников с новой конфигурацией и проверьте доступ к интеграциям, отчётам и OIDC. Не удаляйте старые ключи, пока в очередях, резервных копиях и внешних архивах остаются данные, зашифрованные старым ключом. Особенно важно: зашифрованные `ad_data` в payload ранее поставленных задач `analytics.deliver` **не меняются** этой командой; данные активных грантов отложены (`deferred`) для сохранения идемпотентности повторной отправки, как и старые backup-файлы. Дождитесь обработки/удаления старых задач и обеспечьте срок хранения ключей для восстановления backup.
7. После подтверждения, что ни одна рабочая копия и очередь не зависят от прежнего ключа, старый ключ можно убрать из `*_PREVIOUS_KEYS`. Проверку пригодности старых backup выполняйте отдельно.

## Управление устойчивостью

- `INTEGRATIONS_CIRCUIT_THRESHOLD=5` — целое от 1 до 100.
- `INTEGRATIONS_CIRCUIT_COOLDOWN_SECONDS=60` — целое от 1 до 3600.
- Circuit state находится в `storage/app/integrations/circuits/*.json`, не содержит URL, payload и credentials. При ошибке чтения или записи файлов доставка не выполняется.
- При перебоях Keycloak не отключайте онлайн-проверку OIDC-токенов ради доступности: она нужна для отзыва сессий. Локальные сессии доступны независимо от работоспособности IdP.

## Приёмка

- Без Composer/PDO SQLite: `php tools/security-resilience-regression.php` (vault, tampering, breaker). 
- С реальной PDO SQLite в CI: `php tools/security-resilience-regression.php --require-db` (все шесть legacy-хранилищ, dry-run, apply, повтор, проверка чтения без старого ключа).
- `php tools/integration-regression.php` и `php tools/rate-limit-concurrency.php` подтверждают сохранение прежнего поведения API и конкурентную безопасность.

**Ограничения:** это ротация ключей шифрования vault, **не** смена `APP_KEY`, HMAC-секретов сторонних webhook receivers, JWT-ключей Keycloak, паролей, ключей подписи релизов или backup. Она не перекодирует исторические backup-архивы и payload очередей: до их истечения/миграции старые ключи нужно сохранить. Для multi-node развёртываний требуется синхронное изменение конфигурации на всех узлах и общее хранилище circuit/rate-limit или эквивалент внешнего coordination layer.
