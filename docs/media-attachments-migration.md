# Media & Attachments Migration (CajeerEngine 1.4.6)

This release adds an **operator-executed, resumable binary-file migration** for completed DLE and WordPress projects. It writes to the existing Media Library, not to arbitrary upload paths. It imports every compatible source file in the supplied local uploads mirror, checks file signatures, limits and SHA-256, generates enabled image variants, and replaces matching old upload links in content owned by the project. No source PHP, WordPress plugins, script tags or active content is executed.

## Preparation

1. Finish Discovery → Mapping → Dry Run → Approval → content import (1.4.3 / 1.4.4) and, where applicable, identity creation (1.4.5). The media stage requires the **committed content execution receipt** and database-backed content/CMS storage.
2. Back up the **target database, `storage/` and `public/uploads/` together** before the transfer. This stage performs real changes to physical files and content entries; it does **not** promise an all-or-nothing rollback of an entire file tree.
3. Install migration `0021_migration_media.sql`: `php bin/cajeer migrate`. Keep existing `.env`, `APP_KEY`, `INTEGRATIONS_KEY` and all previous migrations. The metadata catalog may use `MEDIA_STORAGE=file` or `MEDIA_STORAGE=database`; for large sites, use the latter according to `docs/media-library.md`.
4. Mount or copy the source media on the migration host **outside the destination's public uploads folder**. For WordPress, copy `wp-content/uploads` (the command receives that directory itself); for DLE, copy `uploads`. The source directory is read-only to the importer. The source mirror is scanned recursively; symbolic links and path traversal are rejected. Source and target sites may be on separate hosts.

## Usage

```bash
# DLE, given the local copy of the old site's /uploads directory
php bin/cajeer migration:media-import PROJECT_ID /srv/old-dle/uploads --yes --origin=https://old-dle.example.com

# WordPress, given a local copy of wp-content/uploads
php bin/cajeer migration:media-import PROJECT_ID /srv/old-wp/wp-content/uploads --yes --origin=https://old-wp.example.com

# Optional WordPress attachment -> featured image mapping for an existing target media field
php bin/cajeer migration:media-import PROJECT_ID /srv/old-wp/wp-content/uploads --yes --origin=https://old-wp.example.com --featured-field=cover
```

`--origin` is optional and is **only** used for matching old absolute links (no HTTP request or download to that origin is made). It must be the old site's scheme and hostname without a path, credentials, query or custom port. Without it, root-relative `/uploads/...` and `/wp-content/uploads/...` URLs are still rewritten.

`--featured-field` is optional, and must name an existing `media` field in the target content type. WordPress attachment IDs and `_thumbnail_id` relationships are read from the already uploaded encrypted WXR, a read-only WordPress SQL connection, or authenticated WordPress REST metadata. Only images present and verified in the supplied local mirror can be selected. Existing nonempty featured media fields are left untouched. If WordPress metadata cannot be accessed, omit this option; file transfer and ordinary URL rewriting continue to work independently.

### File support and limits

This stage respects the **existing** MediaRepository whitelist: JPEG, PNG, GIF, WebP, PDF, TXT, Markdown, ZIP. MIME must match the extension; images must pass decoder/dimension validation (16 MP ceiling), and each file is limited by `MEDIA_MAX_UPLOAD_MB` (default 25 MiB, maximum 100 MiB). It scans up to 20,000 files and 4 GiB from one mirror; unsupported or invalid files are **reported rather than silently claimed as imported**. Other file types (such as SVG, executable code, office documents, video and proprietary plugin files) are not imported by this release; convert or handle them through a separate reviewed workflow. HTML is not imported as an executable file.

Files referenced from published imported content (or chosen featured images) are public; unreferenced files and those used only in drafts are stored **private** to avoid disclosing restricted attachments. A private media URL requires authenticated download. Publishing such a draft later may require a separate reviewed visibility change. The imported file's public URL (when public) is generated by the active StorageManager. Media SHA-256 deduplication reuses an existing physical file if its checksum and visibility match. The stage stores a durable `(project, relative path) → SHA-256, media UUID` SQL mapping and verifies the referenced physical file on restart. Changed originals cannot overwrite an earlier import invisibly.

### Link rewriting and consistency

The migration iterates **only** content IDs listed in the committed migration execution receipt. Old upload URLs are replaced in recursively nested content data (including rich text) with exact-match boundaries and without touching unrelated external domains. It uses the existing ContentEntryRepository and optimistic revision check; changes made by an editor after the content migration cause a conflict instead of a blind overwrite.

Before saving an entry, the importer persists a pending SQL intent with hashes of old and expected new data. It then uses the normal content update path (which also maintains public routes, revisions and search projections) and marks the intent done. On a crash between those operations, the next run recognizes the expected resulting hash and completes the intent without applying a second update. Once a rewrite is done, later editorial revisions are not overwritten by a repeated run.

The CLI JSON output includes scanned/importable/new/deduplicated files, unsupported and invalid files, updated entries and URLs, unresolved legacy references, unresolvable featured-image IDs, and cumulative SQL receipt counts. Exit codes: `0` completed with no unresolved or unsupported files, `3` completed with explicit omissions requiring attention, `1` execution failed (rerun after repairing the cause), `2` invalid CLI arguments. Do not interpret code `3` as complete migration. The admin's Migration Center displays the cumulative file and rewrite counts.

### Recovery

File import is resumable; it is not one cross-filesystem SQL transaction. If a process stops after a MediaRepository write but before its mapping receipt, SHA-256 deduplication permits recovery. If an entry update succeeds before its done receipt, the pending intent hash permits recovery. On an unsuccessful run, retain the source mirror and rerun with identical arguments. For full rollback of the project, restore the consistent database and file backup taken before the media stage. Never remove target media files manually by filename; other projects may reference a deduplicated object.

### Security and deployment notes

Only the operator CLI can perform physical migration. The HTTP API exposes read-only aggregate progress through the existing Migration Center; there is no arbitrary path-reading HTTP endpoint. The operation uses the application's exclusive lock, refusing an active recovery or extension deployment. WordPress database attachment discovery uses the existing read-only, allowlisted source database connection; REST uses the pinned public-only HTTPS transport; WXR parsing forbids DTDs and external entities. Output contains no source credentials, and encrypted WXR is never returned to the browser.

For release certification, run `php tools/media-migration-regression.php --require-db` (PDO SQLite, DOM, mbstring), `python3 tools/media-migration-sqlite-regression.py`, the existing Media Library regression, and the rest of the project's release pipeline. The actual destination storage and source upload files must be backed up and verified before production cutover.
