# Перенос сайта — CajeerEngine 1.1.5

Portable ZIP v3 переносит данные, а не установку CMS. Backup (`backup:create`) сохраняет всю установку и необходим для аварийного восстановления. Не заменяйте его экспортом.

## Экспорт и перенос

На исходном сервере:

```bash
php bin/cajeer export:create --section=content,media,cms,settings --filename=site.zip --json
```

Скопируйте `storage/app/exports/site.zip` на целевую установку, например в `storage/app/imports/site.zip`. Используйте защищённый транспорт; сравните SHA256 файла с `sha256` в ответе. ZIP содержит `manifest.json`, `data/<section>.json` и `media/<sha256>` с оригинальными байтами. SHA256 проверяет целостность, но не доказывает доверие к автору пакета. Экспорт может содержать неопубликованный контент; храните его как конфиденциальные данные.

- `content`: типы, записи всех редакционных статусов, группы переводов, история ревизий новых записей. Старые soft-deleted записи не входят; прежние версии использовали tombstone и для archived, поэтому такие записи также не входят.
- `media`: метаданные и исходные файлы public-local; дубликаты по SHA256 используют уже имеющийся файл и его метаданные.
- `cms`: конфигурация темы, плоские меню и redirects. PHP-код тем и extensions не переносится.
- `settings`: только `app.name` и `app.locale` из БД. Секреты, `.env`, пользователи, роли, токены и расширения не переносятся; создайте пользователей и установите доверенные расширения отдельно.

Формат JSON v2 с корректным checksum остаётся доступен для совместимости (`--filename=site.json`), но для медиа свыше 16 MiB используйте ZIP. Старые неподписанные checksum форматы v1 не поддерживаются. Из v2 импортируются только поддерживаемые данные; пропущенные секции отражаются в плане.

## План и применение

```bash
php bin/cajeer import:diff site.zip --strategy=update --json
php bin/cajeer import:run site.zip --strategy=update --plan=<plan-digest> --json
```

`--section=content,media` выбирает секции; при отсутствии секций используются доступные в пакете. Повторите те же параметры при подтверждении. `fail` (по умолчанию) блокирует изменения существующих объектов, `skip` сохраняет целевые объекты, `update` обновляет совпадающие записи. Совпадение контента определяется по типу, locale, slug; новые записи сохраняют UUID, существующие сопоставляются по ID. Несовместимые схемы типов и неразрешённые связи блокируют применение. Новый тип получает собственный ID. Новые ревизии дополняют историю существующей записи, исходная история переносится только для новых записей. `skip` оставляет целевые данные и их публичные пути. Не используйте selective import, если отсутствуют обязательные связанные записи или медиа.

План содержит `summary`, `sections`, `mapping`, `skipped`, `sha256`, `plan` и `ok`. План пересчитывается под эксклюзивной блокировкой перед применением; изменённый пакет или целевые данные требуют нового подтверждения. План не удаляет объекты, отсутствующие в пакете. `--delete-missing-content`, `--create-missing-users` и `--settings=replace` отклоняются. `--dry-run` только показывает план.

## Условия безопасного применения

Целевая установка должна быть мигрирована, production CMS должна использовать доступную БД, а хранилище и очередь — профиль восстановления 1.1.4 (local, file/PostgreSQL queue). При переносе контента поддерживаются file/PostgreSQL search; внешний поисковый движок требует отдельного контролируемого перехода и переиндексации. Оператор должен иметь доступ к рабочим данным, БД, коду для полного rollback, и ключу `BACKUP_KEY_FILE` вне проекта. Используйте отдельный операционный аккаунт с общей runtime-группой; `storage/app`, `public/uploads` и вложенные runtime-директории должны иметь group-write/setgid и корректную группу PHP-FPM. Не выдавайте ключ web-процессу. Для PostgreSQL нужны штатные утилиты и владелец БД с CREATEDB, как в [update-backup.md](update-backup.md). Сторонние процессы, напрямую изменяющие БД/файлы, нужно остановить.

Применение создаёт проверенный backup, устанавливает durable recovery marker, применяет данные через репозитории и транзакцию БД, индексирует изменённые записи и сохраняет отчёт в `storage/app/import-reports/`. При ошибке восстанавливает snapshot. Если восстановление не удалось или процесс прерван, сайт остаётся недоступным до восстановления. Не удаляйте marker вручную. Используйте ID из `storage/app/backup-restore.json`:

```bash
php bin/cajeer backup:verify --id=<backup-id>
php bin/cajeer backup:restore --id=<backup-id> --yes
php bin/cajeer doctor
php bin/cajeer maintenance:off
```

Восстановление заменяет данные состоянием snapshot. Проверьте БД, контент, uploads и readiness до снятия maintenance. Копии и отчёты хранятся локально; применяйте отдельную retention/шифрованную offsite policy.

## Admin UI и API

Раздел Import/export создаёт ZIP, скачивает его, загружает пакет, показывает план и создаёт подтверждённый запрос. Запрос не меняет сайт. Оператор выполняет `php bin/cajeer import:requests`, затем `php bin/cajeer import:execute --id=<request-id>`. После исполнения обновите список запросов. Просроченный план требует нового запроса. API использует существующую авторизацию/CSRF. Multipart upload: `POST /api/v1/import-export/upload`, поле `file`; download: `GET /api/v1/import-export/download/{file}`. Результат import — HTTP 202, не завершённый импорт. Для больших пакетов используйте CLI/SFTP; учитывайте web-server, PHP upload и request timeout limits.

## Ограничения размера

Медиа копируются и проверяются потоково. ZIP: до 20 000 медиа, 100 MiB на файл (дополнительно применяется лимит MediaRepository), 4 GiB общий лимит распакованных данных, до 32 MiB JSON на секцию и 64 MiB суммарно. JSON-метаданные и план загружаются в память; это не механизм потокового импорта миллионов записей. Обеспечьте место под ZIP, staging и полный backup, и достаточный memory_limit. При прерывании возможны оставшиеся приватные staging-файлы; удалять их можно после завершения recovery и всех операций.

## Приёмка

```bash
php tools/import-regression.php
php tools/import-regression.php --database
php tools/security-regression.php
php bin/cajeer api:lint --strict --json
```

Первый тест создаёт две независимые файловые установки, проверяет перенос и rollback с реальным SQLite snapshot; `--database` использует PDO SQLite и штатные миграции. Проверка полного production-профиля дополнительно требует установки dist, PostgreSQL и браузерного E2E.
