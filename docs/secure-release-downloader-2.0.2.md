# CajeerEngine 2.0.2 — Secure Release Downloader

## Scope

The production downloader consumes **only** the latest GitHub Release on the configured channel. It downloads the project's published `dist.zip` (never GitHub's autogenerated source ZIP), detached `.sig` and `.sha256`, checks an out-of-band Ed25519 trust key, authenticates every ZIP file through the current `ReleaseArtifactVerifier` and retains the verified package locally. **It does not install, start maintenance or run migrations.** Browser installation is a later roadmap stage.

## Prerequisites

- PHP 8.4.1+, ext-sodium, ext-curl, ext-phar and either ext-zip or `unzip` for full ZIP inspection.
- Outbound TLS access to `api.github.com`, `github.com`, and the GitHub release asset CDN (`release-assets.githubusercontent.com`, `objects.githubusercontent.com`). All resolved addresses must be public. Redirects and downloads never use an HTTP proxy.
- A trusted Ed25519 release public key stored **outside the application root**, provisioned independently from GitHub metadata. Its file must not be a symlink or writable by group/other. Set `UPDATE_TRUSTED_PUBLIC_KEY_FILE=/etc/cajeer/keys/release-public.key` in the protected environment. Never copy the signing private key to a deployed CMS.
- Adequate free disk space for the bounded temporary download, validated release and the subsequent install/backup. Downloader data is kept in private `storage/app/updates/downloads/`.

## Usage

```bash
php bin/cajeer update:check
php bin/cajeer update:download
# Optionally assert the expected latest eligible version:
php bin/cajeer update:download --version=2.0.2
```

The command writes JSON with `ready_to_install`, the absolute local `package`, `sha256` and `next_command` for a verified archive. If the package was already downloaded, the cache is **revalidated against the currently trusted signing key and checksum** before reuse. A stale or offline catalog will not authorize a download; retry once GitHub metadata is fresh.

**Installation remains a separate privileged operator action:**

```bash
php bin/cajeer update:apply --package=/absolute/path/from/downloader.zip --sha256=<verified_sha256> --dry-run
php bin/cajeer update:apply --package=/absolute/path/from/downloader.zip --sha256=<verified_sha256>
```

The existing `update:apply` flow performs backup, compatibility validation, maintenance, migration, post-update checks and recovery. It re-verifies the signed package independently; a downloader receipt is not installation authority.

## Security model and failure modes

- The release identity and all three asset paths must match canonical CajeerTeam GitHub URLs. There is no arbitrary URL/download or user-selected local file argument to the downloader.
- Asset delivery uses TLS verification, public-only pinned DNS, fixed host allowlist, no proxy, up to five validated HTTP redirects and byte/time limits. ZIPs are streamed to private temporary files instead of memory; download content is never executed.
- A signed package is accepted only when `.sha256`, GitHub's digest (if present), detached Ed25519 signature and the ZIP manifest/inventory all agree. Metadata from GitHub alone never establishes trust.
- A failed download or validation leaves no `verified.json` commit marker; temporary files are removed. Reuse of a cached package is conditional on renewed complete validation.
- The downloader is explicitly CLI-only; it does not grant PHP-FPM code replacement privileges. Direct browser use and unattended installation are not part of 2.0.2.
- `UPDATE_DOWNLOAD_TIMEOUT_SECONDS=300` controls the per-asset download timeout (bounded to 15–1800 seconds). `UPDATE_DOWNLOAD_MAX_BYTES=2147483648` limits ZIP size (1 MiB–2 GiB). A space reservation check uses the size GitHub advertises, but is not a disk quota guarantee.

## Verification

```bash
php tools/secure-release-downloader-regression.php
php tools/automatic-release-discovery-regression.php
php tools/github-release-regression.php
```

The offline regression runs signed adversarial fixtures through the real updater and checks that checksum or full manifest failures cannot publish packages. A complete positive dist acceptance requires a built and signed real release and `ext-curl` for actual HTTPS transfer; perform it on staging with the same bytes that will be deployed.
