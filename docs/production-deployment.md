# Production Deployment — 1.2.5

## Supported profile

One dedicated Linux host (systemd 243+), Nginx, PHP 8.4.1+ CLI and PHP-FPM 8.4, PostgreSQL 17+ with matching or newer `psql`, `pg_dump`, `pg_restore`. Python 3.9+, OpenSSL, curl, unzip, flock and standard Linux tools are required. PHP extensions: pdo_pgsql, mbstring, sodium, openssl, fileinfo, phar, gd, curl, DOM/XML and the extensions required by the reviewed Composer lock; pcntl is recommended for graceful CLI job shutdown. Install the matching distribution packages from your approved repositories. This is not a package-manager installer or multi-node orchestrator. The fixed paths and service names are dedicated to one CMS. Other deployments (Apache, MySQL, SQLite, aaPanel, shared PHP-FPM) keep their existing manual instructions.

The target never resolves dependencies or builds frontend assets. It installs the exact signed `-dist.zip` and verifies its SHA-256, Ed25519 signature, manifest, dependency inventory, every file and installed code against the archive. The source-only control plane is separate from the runtime. Install it from a reviewed checkout in `/opt/cajeerengine-deploy` owned by root, not from an untrusted candidate. Do not place the deployment tool under the writable site or give PHP processes root privileges.

## Build and trust

On the build host, `composer.lock` must be reviewed and committed. If the source checkout has no lock, a maintainer must run `composer update --no-install --no-interaction`, review the resolved dependencies and commit the resulting real lock. Do not resolve versions during deployment; the release pipeline refuses unlocked builds. Build with PHP, Composer and Node using:

```sh
export RELEASE_SIGNING_KEY_FILE=/secure/release-signing.key
bash tools/release-pipeline.sh /secure/release-output
```

The signing key stays off the target. Provision the corresponding Ed25519 public key (generated with `php bin/cajeer release:keygen`) and the expected SHA-256 via a trusted channel. Transfer the ZIP and its adjacent `.sig` to a root-owned directory with no group/world-writable ancestors, e.g. `/opt/releases`, with mode 0644. The SHA must come from the approved release, not be computed from an untrusted download and blindly accepted.

## Provision once

```sh
sudo useradd --system --gid www-data --home-dir /var/lib/cajeerengine-runtime --shell /usr/sbin/nologin cajeerengine
sudo install -d -o root -g root -m 0755 /etc/cajeerengine-deploy /opt/releases /srv/cajeerengine /var/lib/cajeerengine-deploy
sudo install -d -o root -g root -m 0700 /etc/cajeerengine-deploy/tls
sudo install -o root -g root -m 0644 deploy/site.example.json /etc/cajeerengine-deploy/site.json
```

Set `site.json` to your lowercase public DNS hostname and dedicated database. Ensure Nginx includes `/etc/nginx/conf.d/*.conf`, its workers run as `www-data`, ports 80/443 and loopback 18085 are free for this profile, DNS and firewall are configured, and TLS certificate/key are valid for the hostname. Install real certificate chain and private key as regular files (root:root, 0644/0600) at `tls/fullchain.pem` and `tls/privkey.pem`. Certificate issuance and renewal are external; renew by replacing these files securely and running `nginx -t && systemctl reload nginx`. The local gate probe checks TLS connectivity and the server response; use a trusted certificate for public traffic.

Provision an empty PostgreSQL database with a dedicated non-superuser login owning that database and `CREATEDB` (required by the existing database restore procedure), access to the `postgres` maintenance database, and no shared application clients. Use a dedicated cluster or appropriate role isolation. `db_sslmode=disable` is allowed only for `127.0.0.1`; use `verify-full` and the runtime user's libpq trust root for remote databases. A role with `CREATEDB` is a deliberate requirement of automatic recovery; do not use a cluster superuser. Use matching or newer client tools in `/usr/bin`.

Create `/etc/cajeerengine-deploy/install-secrets.json` as root with mode 0600 (using a secure editor or secret manager):

```json
{"db_password":"REPLACE_WITH_RANDOM_BASE64URL_32_CHARS","admin_password":"REPLACE_WITH_STRONG_ADMIN_PASSWORD"}
```

The DB password must be 24–128 ASCII base64url characters (`A-Z a-z 0-9 _ -`), due to the existing dotenv writer. The admin password must satisfy the engine's password rules. The first-install secrets are passed through stdin, never CLI arguments. Remove the input file after successful deployment; the application retains its own private `.env`. Provision `release.pub` root-owned 0644 and a distinct externally backed-up `backup.key`, generated by `php bin/cajeer backup:keygen --key=/secure/backup.key`, installed with owner `cajeerengine`, group `www-data`, mode 0600. Keep the backup key off-site separately from encrypted copies. The parent directory must remain root-owned and not writable by the runtime account.

## Deploy and verify

```sh
sudo python3 /opt/cajeerengine-deploy/deploy/production.py deploy /opt/releases/cajeerengine-1.2.5-dist.zip --version=1.2.5 --sha256=APPROVED_64_HEX_SHA256
sudo python3 /opt/cajeerengine-deploy/deploy/production.py status
```

The root controller serializes operations with flock, authenticates a private copy of the artifact, rejects older releases and same-version different content, validates configuration, generates dedicated systemd/FPM/Nginx configuration, tests Nginx/FPM, installs into `/srv/cajeerengine/app`, and runs the real installer with PostgreSQL. The public site stays gated (503 including static assets). It validates installed checksums and migrations, tests the real loopback Nginx → PHP-FPM → DB readiness and version, starts the worker, waits for its heartbeat, starts the persistent scheduler timer, enables the units and durably records ready before removing the gate. On reboot workers and FPM start only when their root-owned permission markers exist. The web installer and updater are disabled at Nginx; use the CLI. Runtime units use read-only systemd mounts for application code, with writable storage/cache/uploads/extensions only. Install or update extensions using approved offline CLI procedures; code-writing web operations cannot modify immutable runtime mounts.

Repeat the same command with identical signed artifact and SHA: it verifies installed files and health without resetting secrets or DB. A newer artifact triggers the existing full backup, journalled update, migrations, postchecks and rollback machinery with workers/FPM stopped. A migration failure or HTTP readiness failure before workers restart triggers recovery to the previous version when possible. Once background workers may have emitted external side effects, automatic rollback is refused and the gate remains closed for an operator decision. Never run a parallel external updater or DB writer during deployment.

## Recovery and limitations

`status` reports the root journal, gate and service states. On interrupted/failed recovery the persistent gate remains closed; investigate `journalctl -u cajeerengine-php -u cajeerengine-worker -u cajeerengine-scheduler`, the application update journal, and `docs/update-backup.md` / `docs/disaster-recovery.md`. For an interrupted update use the documented recovery launcher or `update:rollback --yes` as the runtime user while all runtime services are stopped. If the first attempt failed before the application directory was published, retry the identical artifact after fixing host configuration. For a failed initial install after publication there is no prior DB: preserve diagnostics, repair or restore the dedicated DB and files explicitly; do not blindly rerun against a partially migrated DB. Never remove the maintenance gate by hand. Once the exact signed release has been recovered and the CMS is installed, resume:

```sh
sudo python3 /opt/cajeerengine-deploy/deploy/production.py resume --version=1.2.5 --sha256=APPROVED_64_HEX_SHA256
```

Resume only accepts recorded artifact identities, re-verifies every immutable file, checks recovery markers and readiness and starts the units. The source controller retains the approved artifacts and root journal in `/var/lib/cajeerengine-deploy`; back these up with host configuration, trust key and separate backup encryption key. The CMS backup remains in `storage/app/backups/production`; export encrypted copies off-host using the 1.2.4 disaster recovery commands. Configure independent monitoring, retention and periodic restore drills. No zero-downtime/HA, external DB failover, automatic certificate issuance or OS package locking is claimed.

## Tests

`python3 deploy/test_production.py` exercises path traversal, symlinks, duplicates, safe config, activation gating, real Nginx TLS and static/secret route protection. `deploy/host-smoke.sh` is a destructive disposable-host test with real systemd, Nginx, PHP-FPM, PostgreSQL and a signed dist; it tests installation, login, repeated deploy, tampered ZIP rejection, failed migration recovery, successful newer migration and runtime code read-only mounting. Release CI runs it before uploading verified artifacts. Never run it on a live host.
