# CajeerEngine 1.9.5 — Security & Privacy Hardening

## Границы исправлений

Это **исполняемые изменения PHP**, а не декларативная защита: `UserRepository::consumeRecoveryCode()` выполняет однократный расход резервного кода 2FA в транзакции с блокировкой строки (`SELECT ... FOR UPDATE` на PostgreSQL/MySQL/MariaDB). На SQLite подтверждение обновления сравнивает старую JSON-строку, что блокирует повторное расходование при гонке. При неопределённом исходе операции нельзя считать код восстановленным или повторно запускать login автоматически.

`AuthService::login()` не сообщает, существует ли email, отключена ли учётная запись и включён ли фактор. Для неизвестного пользователя выполняется настоящий Argon2id `password_verify` фиктивного хеша, чтобы не оставлять очевидную быструю ветку. При этом универсальное выравнивание времени для любых хешей и внешних СУБД **не гарантируется**, поэтому на ingress обязательно сохраняется rate limit. Журнал `auth.login_*` пишет SHA-256 email и user ID вместо email. IP адрес и User-Agent всё ещё входят в security audit: retention, удаление и доступ оператора должны быть настроены по политике организации. SHA-256 идентификатор не равен полной анонимизации.

Ошибки `InvalidArgumentException`, `DomainException` и неудачной диагностики БД не включают raw exceptions в production HTTP. Для тестовых окружений (`local`, `dev`, `testing`) текст валидации сохраняется для диагностики. Ошибки расширений, которые могут содержать путь/конфигурацию, также не раскрывают низкоуровневый текст. Runtime logger сохраняет только ограниченный набор полей и имена известных событий, использует закрытый режим файлов `0600` и отклоняет symlink для лога и lock-файла. Runtime-файлы в каталоге с неконтролируемыми правами требуют отдельного исправления прав на файловой системе. Параметры паролей, OTP, recovery-кодов и TOTP secrets помечены `#[\SensitiveParameter]`, чтобы PHP не включал их в аргументы отладочных stack traces.

## Установка и совместимость

1. Перед заменой файлов создать проверенную копию БД и конфигурации, обеспечить остановку PHP workers и фоновых процессов.
2. Наложить архив **только изменённых файлов** на текущую 1.9.4, сохранив структуру каталогов.
3. Проверить принадлежность и права `storage/logs`, `storage/rate-limits`, `.env`; не делать эти каталоги доступными для HTTP и непривилегированных пользователей.
4. Перезапустить PHP-FPM, workers и scheduler; проверить запуск действующей сессии, MFA, одноразовое расходование recovery-кода и обработку штатных ошибок ввода.

**Миграций БД в этой версии нет.** Формат уже существующих захешированных recovery-кодов не меняется. В старом журнале `ce_audit_log` ранее сохранённые email не удаляются автоматически — их удаление требует согласованного retention-процесса и проверки нормативных обязательств.

## Обязательные проверки

```bash
php tools/security-privacy-production-regression.php
php tools/security-privacy-production-integration.php --require-db
php tools/security-hardening-regression.php
php tools/ci-check.php --strict
php bin/cajeer security:doctor
php bin/cajeer ops:check
```

Вторая команда **требует** `pdo_sqlite` и Composer-зависимости, не пропускает тест молча: проверяет одинаковые ответы при несуществующем/отключённом аккаунте, отсутствие plaintext email в новых audit-событиях, одноразовые recovery-коды, конкурентную гонку двух PHP/PDO-подключений, redaction HTTP ошибок и досрочный отказ на слишком большом JSON. Для полного допуска запускаются также `vendor/bin/phpunit --no-coverage`, `composer analyse`, приёмка PostgreSQL/MySQL/MariaDB, negative RBAC/CSRF/OIDC E2E и полный release CI.

## Дополнительная staging-приёмка

- На реальных двух воркерах провести одновременный вход с одним recovery-кодом: только одна операция может пройти, оставшийся код должен быть недействителен.
- Убедиться, что login не раскрывает наличие email, что низкоуровневые сообщения БД/расширений не попадают в HTTP и что секреты не сохраняются в runtime-логах.
- Проверить корректность прав администратора, отзыв сессий после отключения аккаунта, MFA/SSO на реальном Keycloak, утечки на публичных эндпоинтах и expiry токенов.
- Прогнать SAST, проверку зависимостей, динамический vulnerability scan и независимый penetration test. Эти проверки нельзя заменить `php -l` или успешным source release builder.

**Статус:** изменения исходников готовы для приёмки. Официальное подтверждение production-ready требует результатов полного CI и security/pentest для точной развёрнутой сборки; локальный offline-тест не является сертификатом безопасности всей CMS.
