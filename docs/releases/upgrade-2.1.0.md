# Переход на CajeerEngine 2.1.0

### Безопасный порядок для администратора установленной CMS

**[← Релиз 2.1.0](2.1.0.md)** · **[Операторский runbook](../github-auto-updater-ga-2.1.0.md)** · **[Резервные копии](../backup-rollback-integration-2.0.5.md)**

---

> [!CAUTION]
> Этот документ — **контрольный маршрут**, а не универсальный скрипт автоматического обновления. Выполняйте опасные операции только по процедуре для конкретного сервера. Перед изменением рабочей системы проверьте восстановление на отдельном staging-окружении. Не запускайте тесты с разрушением данных на production.

## Карта перехода

| Этап | Контроль | Условие продолжения |
| :-- | :-- | :-- |
| **1. Проверить** | Версия, инфраструктура, совместимость расширений, ключи | Нет блокирующих расхождений |
| **2. Сохранить** | Бэкап БД/медиа/приложения, off-host копия, пробный restore | Восстановление воспроизводимо |
| **3. Подготовить** | Подписанный dist, staging, состояние оператора | SHA-256/Ed25519/манифест прошли проверку |
| **4. Подтвердить** | Отдельные запросы на download/stage и install | Оператор готов, администратор авторизован |
| **5. Принять** | API/UI, БД, worker, scheduler, аудит, уведомления | Нет незавершённой установки и recovery-marker |

## 1. Перед началом

- Уточните **фактически установленную версию** и сравните её с `2.1.0`. Пропуск версий требует проверки совместимости, миграций и активных расширений, а не только сравнения номера.
- Сверьте PHP с `>=8.4.1 <9.0`, используемую БД и расширения; для production основной профиль — PostgreSQL 17+.
- Проверьте наличие и права на `UPDATE_TRUSTED_PUBLIC_KEY_FILE` и `BACKUP_KEY_FILE`. Приватный ключ выпуска хранится вне работающего сайта.
- Оцените свободное место, состояние очереди, scheduler и доступность бэкапов за пределами сервера.
- Не включайте `UPDATE_WEB_UPGRADE_ENABLED=true` / `UPDATE_OPERATOR_ENABLED=true`, пока не установлен и не протестирован отдельный non-root оператор.

Уточнения: [требования GA](../github-auto-updater-ga-2.1.0.md) и [production deployment](../production-deployment.md).

## 2. Проверить staging

На отдельной копии установки воспроизведите процесс с **тем же типом СУБД, версией PHP, настройками хранения и активными расширениями**, что используются в production.

1. Получите из [официального релиза](https://github.com/CajeerTeam/CajeerEngine/releases/tag/v2.1.0) `cajeerengine-2.1.0-dist.zip`, его `.sha256`, `.sig` и манифест.
2. Проверьте подпись через независимо предоставленный доверенный Ed25519 public key и проверьте ZIP-манифест. Не ограничивайтесь вычислением хеша скачанного файла без доверенного источника.
3. Сделайте зашифрованную резервную копию и восстановите её на копии стенда. Зафиксируйте результат без публикации секретов.
4. Убедитесь, что обновления не проводят повторно прерванные транзакции и что отказ оператора блокирует новые HTTP-подтверждения.
5. Проверьте штатное обновление и отдельно — откат на одноразовой восстановленной копии. Откат может уничтожить последующие записи.

> [!WARNING]
> Блокировка при `recovery_required`, `heartbeat_missing`, `heartbeat_stale` или `operator_busy` — защитный механизм. Не исправляйте состояние ручной записью `operator-status.json` и не обходите зафиксированный журнал.

## 3. Настроить оператора

Инструкция предусматривает `cajeerengine-update-operator.timer` и выделенного пользователя `cajeer-updater` с минимально необходимыми правами. Таймер должен выполнять реальный опрос, после которого сохранится актуальный статус.

```bash
# Диагностика — читать можно до попытки установки
php bin/cajeer update:status

# Проверка сервиса на сервере с systemd
systemctl status cajeerengine-update-operator.timer
journalctl -u cajeerengine-update-operator.service
```

Ожидается `operator_ready`, отсутствие recovery-marker и возраст heartbeat в пределах `UPDATE_OPERATOR_MAX_HEARTBEAT_AGE_SECONDS` (по умолчанию **180**). Настройка флагов без живого systemd-оператора не обеспечивает готовность.

> [!IMPORTANT]
> Документированный root-managed deployment preset может блокировать запись non-root оператора. Не выдавайте PHP-FPM-процессу права на установку кода; согласуйте владельцев и группы по [GA runbook](../github-auto-updater-ga-2.1.0.md) и проверьте права на реальном хосте.

## 4. Обновить через Admin Update Center

В разделе `/admin/#/updates` (Static SPA) или `/updates` (Nuxt) действуйте последовательно:

1. **Check GitHub** — проверьте обнаруженный выпуск, установленную версию и статус оператора.
2. **Download and stage** — создайте одноразовый подтверждённый запрос; дождитесь завершения загрузки и криптографической проверки.
3. **Install** — отдельно подтвердите установку **новой** подготовленной версии. Повторная проверка пакета, preflight, backup, maintenance и postcheck проходят на стороне оператора.
4. При ошибке читайте аудит и операторский журнал. Не повторяйте вслепую прерванную команду и не удаляйте recovery-маркеры вручную.

Публичный веб-интерфейс не должен скачивать исполняемые архивы и непосредственно выполнять установочные команды. Наличие новой версии не запускает установку автоматически.

## 5. Принять результат

- [ ] Версия `VERSION` и `release.json` соответствует `2.1.0`; активные assets согласованы.
- [ ] Успешно выполняется `php bin/cajeer doctor`, API и публичные страницы отвечают.
- [ ] У администратора корректно работают вход, ограничения ролей и критические подтверждения.
- [ ] Миграции завершены; данные, медиа и поиск не повреждены.
- [ ] Worker, scheduler, уведомления и webhook-outbox проверены отдельно.
- [ ] История обновления содержит итог операции, а статус оператора не требует восстановления.
- [ ] Сохранены сведения о **точном подписанном артефакте** и результатах staging-приёмки.

## Если обновление не завершилось

**Не включайте сайт принудительно и не стирайте журнал операции.** Повторное применение обновления при неоднозначном состоянии может ухудшить повреждение. Используйте [инструкцию по инцидентам](../operations-incidents-1.8.8.md), [runbook восстановления](../operations-recovery-1.8.8.md) и [hardening/recovery документ](../update-production-hardening-2.0.7.md). Восстанавливайте данные только после оценки потери записей, сделанных после обновления.
