## Главное

CajeerEngine 2.1.0 завершает продуктовый контур GitHub Auto-Updater GA. Центр обновлений больше не полагается лишь на флаг «оператор включён»: перед постановкой опасного действия он проверяет **недавний реальный heartbeat** из отдельной системной службы. Неподготовленные или неоднозначные установки блокируются до устранения причины.

> **Идея выпуска:** доступность новой версии ≠ разрешение её установить. Скачивание, применение, backup и rollback требуют подтверждённого состояния системы и полномочий администратора.

## Что изменилось в 2.1.0

### 01 / Проверка готовности оператора

- Проверяется реальный heartbeat процесса `UpdateOperator`, а не только включённые настройки.
- При остановленном таймере, устаревшем heartbeat или маркере восстановления постановка новых запросов блокируется.
- Админка показывает ограниченные диагностические поля: готовность, причину недоступности и возраст статуса.
- Параметр `UPDATE_OPERATOR_MAX_HEARTBEAT_AGE_SECONDS` по умолчанию равен **180 секундам**; допустимый диапазон — **60–3600**.

### 02 / Безопасное применение подготовленного выпуска

- Сверяется установленная версия: уже установленный выпуск нельзя повторно предложить к установке.
- Проверяется наличие и актуальность staged-пакета.
- Перед выполнением оператор **повторно проверяет** SHA-256, Ed25519, ZIP-манифест и готовность восстановления.
- Невалидные или неоднозначные состояния приводят к отказу, а не автоматической повторной попытке.

### 03 / Проверяемость и регрессии

- Добавлены проверки отказа при устаревшем/отсутствующем heartbeat.
- В релизный CI включены сценарии отказов очереди, восстановления и согласования статусов.
- История, события и уведомления из предыдущих шагов ветки 2.0.x сохраняются.

## Как выглядит штатный сценарий

```text
Найти релиз → Скачать и проверить → Подготовить staging
                                      │
                                      ▼
                     Подтверждение администратора
                                      │
                                      ▼
              Heartbeat + preflight + backup + подписи
                                      │
                                      ▼
                    Установка + postcheck + аудит
```

При ошибке обновление не должно молча превращаться во вторую установку. Для ситуаций `recovery_required` предусмотрено **ручное** вмешательство по эксплуатационной инструкции.

## Безопасность и ограничения

> [!WARNING]
> **Rollback уничтожает изменения после обновления** для затронутых данных и файлов, возвращаемых из снимка. Перед восстановлением сохраните вне площадки актуальные копии и согласуйте последствия с ответственным оператором.

- Требуются два **разных** доверенных секрета: публичный ключ для проверки подписанного релиза и защищённый ключ шифрования резервной копии. Приватный ключ подписи не должен находиться на CMS-сервере.
- Нельзя считать рабочим механизм обновления при отсутствии живого оператора, даже если в `.env` включены флаги.
- Корневой (root-managed) deployment-профиль и выделенный non-root updater нельзя совмещать без отдельной настройки прав и тестирования.
- Реальная доставка webhook-уведомления зависит от очереди и приёма внешним получателем.
- Успешная локальная регрессия, зелёный CI или опубликованный релиз не заменяют **приёмку конкретного подписанного dist на staging** и проверку восстановления для выбранной СУБД.

## Что проверить перед обновлением

- [ ] Получен подписанный `dist` именно для 2.1.0; подпись проверяется доверенным ключом.
- [ ] Пройдены все обязательные проверки и проверка совместимости расширений.
- [ ] Подготовлен backup, отдельно сохранены ключи и проведена проба восстановления.
- [ ] На стенде проверены PostgreSQL/выбранная БД, Nginx, PHP-FPM, worker и scheduler.
- [ ] Таймер обновлений работает, `update:status` сообщает о готовом операторе.
- [ ] Есть план действий при `recovery_required`; пользователь не обходит блокировку вручную.
